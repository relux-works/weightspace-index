# Patch formats: three different kinds of change

**Inferred taxonomy for the index**, grounded in the [pinned reuse design](https://github.com/relux-works/model-patcher/blob/33ab004bd5a5ff31134289e26e67be062320f682/docs/reuse-routes.md) and [catalog design](https://github.com/relux-works/model-patcher/blob/33ab004bd5a5ff31134289e26e67be062320f682/docs/catalog-and-evidence.md). This is format guidance, with no real entry or supported application claim. A container extension does not determine the treatment: safetensors can hold model weights or adapter factors; GGUF alone does not identify a quantization recipe.

| | Sparse exact replacements | LoRA adapter | Merged/baked whole artifact |
|---|---|---|---|
| What it contains | Named tensor-local positions and exact replacement bit patterns relative to an exact base. | Low-rank factors plus adapter configuration, resolved target modules and scaling. | Complete resulting model files, including all required sidecars and notices. |
| Why choose this kind? | Preserve a particular sparse edit exactly when its format and base are qualified. Size depends on actual encoded changes and framing. | Represent an update with low-rank factors, often smaller than a dense update; select/apply a compatible adapter at runtime or merge it through a qualified route. Rank and coverage govern what it can represent. | Load or share a self-contained result without the original patch/adapter application stack, subject to rights and runtime support. |
| What binds identity? | Whole-base digest, patch digest/size, format/version, tensor names, dtype/shape, coordinates and before/after expectations. | Base and factor/config digests, rank/targets, scale, order, composition policy and runtime. A runtime descriptor is not a hash of unseen adapted weights. | Complete output inventory/digests plus base, ordered inputs, transformation/backend versions, settings and input/intermediate identities in a provenance manifest. |
| How it reaches a runtime | A qualified format-specific applicator creates a separate model first. No general sparse runtime interface is assumed. | A supported runtime consumes the adapter, or a compatible exporter merges it into a separate model. These are distinct treatments. | The runtime loads the completed output in its own supported format/profile. |
| What it does not promise | It is not a LoRA, an additive floating-point delta or a packed-GGUF byte-offset recipe. It need not be reversible without old values. | It does not reproduce an arbitrary sparse exact edit. Loading factors is not merging, and merging is not automatically lossless or faster. | It is not necessarily a compact patch. A new hash proves inventory identity, not the correctness or benefit of the transformation. |

**The LoRA rationale belongs only to LoRA.** A sparse edit has no low-rank branch to remove. A whole artifact may originate from sparse replacement, LoRA merge or another transformation; its file format cannot establish which. The template separates each kind's required fields, and the schema refuses the other kinds' rationale/route blocks.

For ordinary LoRA layers, runtime computation adds factor projections to the base result; a materialized merge can remove that branch. **Documented mechanism, unmeasured performance:** see the primary [llama.cpp graph implementation](https://github.com/ggml-org/llama.cpp/blob/26d52b0f9543f441fc2bfa383557c992a4fbf4b9/src/llama-graph.cpp) and [adapter export documentation](https://github.com/ggml-org/llama.cpp/blob/26d52b0f9543f441fc2bfa383557c992a4fbf4b9/tools/export-lora/README.md), accessed 10 November 2026 UTC. No universal speed or size claim follows. Quantized merges can change affected-tensor precision and file size; the exact output profile needs its own evidence.

**Inferred delivery rule:** copy-on-bake preserves the base and writes to an owned new destination. A future route must stage outputs, bind ordered inputs, verify expected tensors/files and required sidecars, retain applicable licenses and publish a complete provenance manifest only after success. Wrong input, source aliases, existing destinations, cancellation, timeout, disk-full and partial writes must never overwrite originals or report a completed result. Runtime import/registration is a separate operation. These are requirements, not tested capabilities in this scaffold.

Exact bit equality, logical tensor equality and whole-file equality are different claims. Headers, serialization and recompression can change file digests without changing tensors. Quantization and adapter merging are not generally invertible. A native edit, native-edit-then-quantize, direct quantized edit, runtime adapter and merged adapter require distinct treatment identities and comparisons. Quality stays UNKNOWN until the exact treatment/profile has assessment evidence.
